# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Firmware for the flight side of a drone. The full system is planned as an STM32 (this firmware), a Raspberry Pi Zero 2W (comms/data streams to ground) and a Linux ground station. Today the repo holds just one bare-metal (no RTOS) test project, `G070RB_TestPrj`, for an STM32G070RB (Cortex-M0+). It is used to develop and try out sensor and actuator drivers. Planning notes in `Docs/Analisi/` describe a future FreeRTOS architecture (FlightControl / ReadSensors / ExtCommunications threads, MAVLink). None of it is implemented yet. Documentation, comments and README are mostly in Italian.

## Setup

Sensor drivers are git submodules. Fetch them after cloning:

```sh
git submodule update --init --recursive
```

Each driver (`G070RB_TestPrj/Drivers/drv-*`) is its own repo (github.com/tmx37/drv-*). Commit driver changes inside the submodule first, then commit the updated submodule pointer in this repo.

## Build / flash / debug

Toolchain: STM32CubeCLT (CMake, Ninja, `arm-none-eabi-gcc` and `STM32_Programmer_CLI` must be on PATH; installed under `C:/ST/STM32CubeCLT_1.18.0`). Run commands from `G070RB_TestPrj/`:

```sh
cmake --preset Debug               # configure -> build/Debug (also: RelWithDebInfo, Release, MinSizeRel)
cmake --build --preset Debug       # produces build/Debug/G070RB_TestPrj.elf
STM32_Programmer_CLI --connect port=swd --download build/Debug/G070RB_TestPrj.elf -hardRst -rst --start
```

`G070RB_TestPrj/.vscode/` has matching tasks ("Build + Flash", "CubeProg: Flash project (SWD)") and cortex-debug launch configs for ST-Link. There are no unit tests or lint targets. Firmware is checked on hardware, with debug output over `huart2` (UART).

**Known issue:** `CMakeLists.txt` lists sources/includes under `Drivers/DrvESC_PWM/`, which does not exist in the repo. Configure fails with "Cannot find source file" until those entries are removed or the driver is added. The `CMakeCache.txt`, `build.ninja`, `CMakeFiles/` etc. in the `G070RB_TestPrj/` root are stale, tracked leftovers from an old in-source build. Real builds go in `build/<preset>` (gitignored).

## Architecture

- **STM32CubeMX-generated code**: `G070RB_TestPrj.ioc` is the source of truth for pins, clocks and peripherals (I2C1, USART1/2, TIM1 PWM). `Core/Src/main.c`, `stm32g0xx_it.c`, `stm32g0xx_hal_msp.c`, `cmake/stm32cubemx/CMakeLists.txt`, the HAL/CMSIS under `Drivers/` and the startup/linker files are regenerated by CubeMX. Put hand-written code only between `/* USER CODE BEGIN ... */` / `/* USER CODE END ... */` markers, or regeneration erases it. The top-level `CMakeLists.txt` is user-owned. Add new sources and include paths there (`target_sources` / `target_include_directories`).
- **`main.c` is a test harness**: `#define` switches (`READ_BMP180`, `READ_MPU60X0_GYRO_ACCEL`, `READ_MPU60X0_BOLLA_TEST`, `READ_HMC5883L_BUSSOLA`, `PWM_BRUSHLESS_CONTROL`) choose which driver is initialised and exercised in the super-loop. The ESC/brushless PWM test drives `TIM1->CCR1` directly. The big comment block there holds reverse-engineered ESC throttle ranges (~45880 = 0%, ~64879 = 100%) and the calibration/programming procedures.
- **Driver pattern** (each `drv-<sensor>-gy85` submodule): `Inc/` holds the hardware-agnostic driver API, `Src/` the implementation, `Cfg/` the board binding. The driver never calls HAL directly. It gets a `Drv<X>_Config_t` struct of function-pointer callbacks (I2C read/write register, is-device-ready, master TX/RX, delay) plus a `Drv<X>_Settings_t` struct of register settings. `Cfg/Drv<X>_Cfg.c` fills both, wiring the callbacks to `Core/Src/DrvI2c.c`, and exposes a single `Drv<X>Cfg_Init()` that `main.c` calls. New drivers should follow this layout and must be added to the top-level `CMakeLists.txt` (both the `Src` and `Cfg` `.c` files plus `Inc`/`Cfg` include dirs).
- **`Core/Src/DrvI2c.c`**: a thin HAL wrapper used as the drivers' callback set. It ignores the `I2cInst` argument and always uses `hi2c1`.
- **`UtlGen.h` / `UtlGen_cfg.h`**: shared utility header. Every driver function returns `UtlGen_Err_t` (`UTLGEN_OK` = 0, negative `UTLGEN_ERR_*` codes). It also provides assert, CRC and byte-swap macros. `UtlGen_cfg.h` sets it up for no-OS use.
- `Core/Src/DrvPWM.c` is an unimplemented stub and is not in the build.
- `Docs/` holds the sensor datasheets (GY-87 module: MPU6050, HMC5883L, BMP180), the STM32 HAL reference and the architecture notes.
